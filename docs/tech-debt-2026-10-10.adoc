*Finding (new).* `docs/PALIMPSEST.adoc` states "This project is licensed under
the *Palimpsest-MPL License 1.0 (PMPL-1.0)*" and instructs the reader to "Include
the PMPL-1.0 license text in `LICENSE`". Its badge is internally inconsistent too
— the image URL is `License-MPL--2.0`, the alt text `License: PMPL-1.0`. None of
this matches the tree: `LICENSE` is MPL-2.0, every source header is MPL-2.0, and
`Cargo.toml` publishes `MPL-2.0`. The estate migrated EUPL-1.2 → MPL-2.0 on
2026-05-22 (`docs/DESIGN.adoc` DR-010) and PMPL was never adopted here.

*Recommended next move:* an owner decision, not a cleanup. Either (a) the document
is describing the licence the project *intends* to adopt, in which case `LICENSE`,
`Cargo.toml` and every per-file SPDX header are wrong and must move together; or (b) the
document is a retained statement of the palimpsest *philosophy*, in which case it
must stop asserting the licence in the present tense. Option (b) is a two-line
edit; option (a) is a relicensing. This audit does not pick, because a licence is
not a formatting concern. The estate check that would catch it is
`standards/scripts/check-licence-consistency.sh`, and it is not wired into this
repository.

*Secondary finding.* `REUSE.toml` shipped nine paths that no longer existed
(`Mustfile`, `manifest.scm`, `hooks/*.sh`, `ARCHITECTURE.adoc`, `GOVERNANCE.adoc`,
`MAINTAINERS`, `MAINTAINERS.adoc`, `SECURITY.adoc`, `.well-known/security.txt`)
and REUSE never complains about an annotation whose target is gone — it simply
stops licensing anything. Fixed 2026-10-10: `REUSE.toml` is now limited to files
that cannot carry an in-file header. The reason nobody had noticed is section 6.

*Finding — a gate that could not run.* The only `reuse lint` invocation in this
repository is a GitLab job, and the GitLab pipeline could not be created: the
`trufflehog` job declared `stage: security` while `stages:` listed `lint`, `test`,
`build`. GitLab rejects that at pipeline creation, so *every* job in that file —
fmt, clippy, `reuse lint`, unit tests, doc tests, release build — has been dead
while the file itself looked maintained. Fixed here (stage added) as a side
effect of moving the file to `ci/`, which is also the RSR-canonical location and
requires the out-of-band GitLab project setting *CI/CD configuration file* =
`ci/.gitlab-ci.yml` (see `ci/README.adoc`). Until that setting is applied, the
repaired pipeline still will not run — the fix is necessary, not sufficient.

*Finding — the same class of failure, one level up.* All four checks in
`.github/hooks/` (formerly the root `hooks/` directory) were unreferenced by
anything: no `core.hooksPath`, no pre-commit config, no Justfile recipe, no
workflow step — the only mentions of them anywhere were a `REUSE.toml` glob and a
CHANGELOG line. Being unreferenced was the symptom; two of the four were also
unusable. `validate-codeql.sh`
exited 1 on a clean tree with *no output at all* — `set -euo pipefail` plus a
`find | grep | head` probe makes an empty result a fatal status, and a Rust-only
repository has no `.js` files to find — while `validate-sha-pins.sh` demanded a
rule this repository deliberately does not follow (it pins by version in the YAML
and records SHAs in `actions.lock`), producing 27 false alarms. Fixed:
`.github/hooks/pre-commit` + `install.sh`, and the two broken validators repaired
or re-pointed at the canonical script.

*Finding — unenforced obligations.* `.machine_readable/contractiles/must/Mustfile.a2ml`
said "Run with: `must check`" for a `must` binary that does not exist here, and
six of its checks named root files that had moved. It is now executable
(`scripts/run-mustfile.sh`, run strictly in CI). The general rule: *an obligation
file with no runner is documentation pretending to be a gate*.

*Finding — the new gate was itself wrong, and only CI could say so.* The first run of
`Estate Rules` (2026-10-10, PR #115) went red on `Mustfile obligations hold (strict)`,
and neither the local run nor any amount of reading predicted which of 22 checks: the
sandbox has no `gawk`, so `actions-lock-in-sync` skipped there and ran in CI, while
`signed-commits` did the opposite. Two defects fell out of that difference. First,
strict mode escalated *every* unevaluated or warning-level failure to a critical one,
so the contract's own declared-unmet advisory (this repository has no signing key —
the file says so in its `notes:`) became a hard failure: the gate was reporting the
state of the runner, not of the repo. Strict mode now escalates a skip *at the check's
declared severity* only. Second, `check-lock-sync.sh` needs awk's 3-argument `match()`,
so the gate's verdict silently depended on which awk the image shipped; the workflow
installs `gawk` explicitly instead. Both defects were invisible from a laptop, and both
point at the same rule as the dead GitLab pipeline above: a gate is not real until it has
been observed running where it will be enforced.

*Consequence for future edits:* `.machine_readable/root-allow.txt` counts as an
exemption ledger to the estate's `Exemption ratchet`, so adding a root entry requires a
`Ratchet-exception: .machine_readable/root-allow.txt — <why>` line in the commit message
or PR body. Expect that demand, do not satisfy it by moving entries into comments —
which would keep the count flat by disarming the check.

*Recommended next move:* wire `standards/scripts/check-licence-consistency.sh`
(section 2) and `check-rsr-profile.sh` into CI *when* their blockers are closed
upstream (section 7); a gate added red-by-construction gets disabled within a
month, which is worse than not adding it.
